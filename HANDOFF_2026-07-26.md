## 1. DONE — Paramedic seats now go by credential, not rank

**The bug you saw:** an Engineer who is a paramedic couldn't be dropped into a
Medic's paramedic seat.

**What was actually wrong:** the seat check was already credential-based — it
reads `certs`, and the employee editor already lets you tick "Paramedic" on
anyone. The problem was one line in the roster import
(`applyRosterImport`, `app.js`): every re-import did
`existing.certs = emp.certs`, and `emp.certs` comes from `defaultCertsForTitle()`,
which is purely rank-derived (`Engineer → ["engineer","emt"]`). So each roster
import silently wiped every paramedic license you'd granted by hand.

**The fix** (`app.js`): medical licenses are now merged forward instead of
overwritten. Rank still comes from the roster spreadsheet; the license stays with
the person.

```js
const LICENSE_CAPABILITIES = ["paramedic", "emt"];   // person-held, not rank-derived
...
const heldLicenses = (existing.certs || []).filter((c) => LICENSE_CAPABILITIES.includes(c));
existing.certs = Array.from(new Set([...emp.certs, ...heldLicenses]));
```

**What you need to do:** re-tick "Paramedic" for the engineers/officers who hold
one (Admin → Employees → pick person → Credentials). It will now survive every
future roster import. No backend or migration needed.

## 2. DONE — Apparatus no longer belong to a platoon

**The bug:** each `Unit` had a fixed `shift` (E116=B, E115=C, L115=A…), and every
screen filtered on `unit.shift === getShiftForDate(date)`. Result: a truck only
appeared on 1 day out of 3. In reality the truck is always there; the *platoon on
duty that day* staffs it.

**The new rule**, in two small functions in `app.js`:

```js
unitRunsOn(unit, date)   // front-line unit → always true
                         // on-demand unit  → only if activeDates includes the date
unitsForDate(date)       // replaces every `visibleUnits().filter(u => u.shift === shift)`
eligibleEmployeesForDate(date)  // who can ride = the platoon on duty that date
                                // (supervisors still see everyone, for OT cross-staffing)
```

Every filter site was switched over: day view, week calendar, month grid,
staffing alerts, seat dropdowns, the fallback single-dropdown card, and the demo
seeder. Persisted data is migrated on load by `migrateUnitShiftModel()`, which
sets `onDemand: false` / `activeDates: []` and deletes the old `shift` field.

**Backend** (`fdchecklist/scheduler/`):

- `models.py` — `Unit.on_demand` (bool) + `Unit.active_dates` (JSON list of ISO dates).
  `Unit.shift` is left in the table but marked deprecated and no longer read, so
  rollback is just reverting code — no data loss.
- `migrations/0003_unit_run_rules.py` — hand-written, additive only.
- `serializers.py` / `views.py` — round-trip `onDemand` / `activeDates`, stop
  round-tripping `shift`.

## 3. TO BUILD — Credentials editable in the scheduler, reflected in checklists

**Where things stand:** credentials already live in the *scheduler* database
(`scheduler.Employee.certs` / `.ride_up` on Railway Postgres) and are already
editable from the scheduler UI (Admin → Employees). What lives on the checklist
side is the *Django admin*, which happens to be the only admin UI you've been
using — so it feels like checklists owns them.

So this is smaller than it sounds. The real gaps:

1. **Checklists doesn't read certs at all.** `scheduler/integrations.py` currently
   only answers "who's assigned to this unit today." Add
   `employee_credentials(email)` alongside it, and surface the certs as pills next
   to each crew member on the checklist run page. One helper + one template edit.
2. **Two employee tables.** `checklists` has Django `User` records; `scheduler`
   has `Employee` records. They're joined by email, which is already the
   documented identity anchor. Don't merge them — add a read-only "Credentials"
   panel on the checklist side that resolves through `scheduler.Employee` by email.
   One source of truth, no sync job, no drift.
3. **Guard rail worth having:** block (or at least warn on) completing a checklist
   run for a Medic unit if no crew member holds `paramedic`.

**Recommendation:** do #1 and #3, skip any bidirectional sync. Any design where
credentials are written in two places will eventually disagree, and in a fire
department a stale paramedic flag is an operational problem, not a data problem.

## 4. TO BUILD — Per-platoon staffing templates, pushed out months at a time

This is the biggest of the four and should be its own session. Design, based on
what you described (each truck has a different crew per platoon):

**New state key** — `staffingTemplates`, one row per truck per platoon:

```js
{
  unitId: "E115",
  shift: "A",                                   // which platoon this crew is
  seats: { Officer: "ROSTER-014", Driver: "ROSTER-031", FF1: "ROSTER-052" },
  effectiveFrom: "2026-08-01",
  effectiveTo: null                             // null = open-ended
}
```

**Generate, don't compute on the fly.** A "Push staffing" action writes real
`Assignment` rows for every date in a range: for each date, look up
`getShiftForDate(date)`, find the template for that unit + platoon, and write the
seats. This matters because:

- PTO/sick edits are then just normal single-date assignment edits — the thing
  your supervisors already know how to do. No "exception layer" to reason about.
- The schedule you see is the schedule that's stored. Nothing changes retroactively
  when someone edits a template, which is what you want for auditability.

**Rules to build in:**

- Push is **additive and non-destructive**: never overwrite a date that already
  has a manual assignment. Show a preview — "will create 1,240 assignments across
  87 dates, skipping 14 dates that already have manual entries" — and require a
  confirm.
- Every generated assignment gets `source: "template"`; manual edits flip it to
  `source: "manual"` and become immune to future pushes.
- Re-pushing over a range should be safe to run twice (idempotent).
- Audit-log the push as one entry, not 1,240.

**Roughly:** new `staffingTemplates` model + migration, a template editor screen
reusing the existing seat-dropdown component, a push dialog with preview, and a
`source` column on `Assignment`. Half a day to a day of work.

**Do item 4 before item 3** — item 2 above just made every truck visible every
day, and item 4 is what actually fills them in without hand-entering every shift.
